# Inclusion policy

## Include

A project can be listed when its open-source portion is publicly inspectable and meaningfully usable, and when the stated alternative relationship is useful to readers.

## Open-core projects

Open-core projects are allowed **only when clearly labeled**. The catalog should identify the open-source edition/core, not imply that proprietary enterprise modules are open source.

## Do not include as “open source”

Do not label a product open source merely because:

- its source can be viewed;
- it is free of charge;
- it allows self-hosting;
- it has a “community” edition without an open-source license;
- the license restricts fields of use, competitors, commercial use, or redistribution in ways incompatible with standard open-source definitions.

A separate future list may track source-available software, but it should not blur the distinction.

## Project health

Dormant projects may remain when they are still useful, but the notes should say so. Prefer maintained projects for new additions.

## Neutral comparisons

This project maps **jobs to be done**, not brands to moral judgments. Proprietary products may be excellent. The catalog's purpose is simply to make open alternatives discoverable.

## Runtime and setup metadata

A new project entry must include a useful official `setup_url`, at least one practical platform/runtime tag, and at least one concise limitation / “things to know” tag. These fields are meant to answer a user's first migration questions: **Can I run it? How do I start? What should I know before switching?**

Prefer official installation, download, quick-start, or usage documentation over third-party tutorials. When no dedicated setup page exists, the official upstream README is an acceptable fallback.
